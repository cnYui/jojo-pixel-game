# 角色美术精度：4 个方案对比（2026-10-09）

用户反馈：“游戏的角色图是不是可以做得再精细一些，现在看上去还是太粗糙”。这里只是**样稿和评估**，没有改任何游戏文件（引擎、剧情、assets、data 都没碰），受保护目录（源码 / 角色图集 / 烘焙脚本 / 剧情分镜 / 音频 / 银魂）也只读。

## 四个方案

### 方案 0 · 现在
世界层 320×180，屏幕 1280×720 上每个像素是 4×4 的方块。角色身高 47–56 像素，脸只有 13×8 像素左右，眼睛是一个白点 + 一个青点 + 一个黑点。对话头像 32×32 放大 2 倍；**必杀切入把 32×32 头像在世界层再放大 4 倍，屏幕上每个像素是 16×16 的色块——这是现在全游戏最“粗”的地方**。

### 方案 C · 算法放大（像素画专用放大算法）
自己用 numpy 实现了 Scale2x（EPX）和 2xBR（xBR，带 / 不带混色）三种，在同一场景里比过，**xBR 带混色效果最好**（Scale2x 几乎看不出区别）。做法：角色和背景都放大 2 倍，世界层 640×360，再 ×2 显示。

- 效果：斜边和圆角稍微圆一点，描边边缘多一圈过渡色。**细节一点没变多**——眼睛还是那三个点，帽徽还是一个方块；1:1 看和现在差别很小。
- 优点：全自动，91 个角色、996 帧身体、175 张头像、73 套背景一条构建命令就转完。
- 缺点：效果弱；混色会产生调色板外的颜色和半透明边（引擎的光环、剪影、描边、抖动透明都按“alpha>0 就是身体”算，会多出一圈毛边）；背景天空的抖动纹理会被糊掉一点；引擎改动量和方案 A 一样（世界层要变 640×360），花了引擎的成本却拿不到细节。
- **不推荐。**

### 方案 A · 精度翻倍重画
世界层改成 640×360，承太郎和白金之星按 2 倍分辨率**逐像素手工重画**（承太郎 64×98 画布、白金之星 100×114，身高 94 / 110 像素），花京院仍是算法放大，作对照；背景先沿用原图（最近邻 ×2）。

- 承太郎：帽顶 / 帽檐受光和反光、金帽徽、帽子后沿撕成 4 束头发（每束上沿亮边 + 束间暗缝）、耳朵和鬓角、压低的粗眉、细长的眼（上眼皮粗黑线 + 青绿瞳孔 + 瞳仁）、鼻梁高光、嘴线、下颌角、立领左右两片和前合口、金链一节亮一节暗、外套翻边亮线、三颗金纽扣、肘褶、袖口插进口袋、远侧手臂和前片分开、衬衫明暗、皮带金扣、下摆褶线和里衬、裤缝高光、鞋面高光。
- 白金之星：手画脸（头带、眉弓、发光的眼、鼻、嘴）、发束线 + 受光发束；胸肌下沿、腹白线、三排腹肌、前锯肌、肩 / 二头肌、大腿股四头肌和膝盖分界线，再按“光从左上来”对每种材质统一做受光边 / 背光边；护肩、护腕、拳头点高光。
- 调色板：原色一个不换，每种材质只在明暗阶里补 1 级（`src\palettes.py` 里标了“新”）；描边从 2px 削成 1px。
- 尺寸、脚点、身高比例和原图完全一致（都是 2 倍坐标），碰撞框 / 站位数值乘 2 即可。
- 效果：1:1 看就能认出五官、帽徽、金链、纽扣、肌肉，是 4 个方案里场景小人唯一“变精细”的。
- 缺点：工作量最大（见下表）；只重画主角团的话，旁边没重画的敌人 / NPC / 背景是 4×4 像素、主角是 2×2，像素密度混在一起（总图第一排右边：重画的承太郎站在原样背景前、旁边是算法放大的花京院，能看出密度不一样）；引擎要改世界层（见下文）；手机上世界层像素多 4 倍。

### 方案 B · 场景小人不变 + 高清立绘
世界层不动。对话头像和必杀切入换成 **128×128 的高清像素立绘**（样稿：承太郎半身，远侧手压帽檐的经典姿势，眼睛在帽檐阴影里发亮）。

- 对话框：立绘按 UI 层 1:1 画（屏幕上每个像素 2×2、整张 256×256），半身压在对话框左边、头探出框外，后面垫一块亮一点的底，文字整体右移；版式其余照现在的 `engine\ui.js`（框、名牌、点阵字、翻页三角都是照代码画的）。
- 必杀切入：同一位置、同样占半个屏幕，从“每像素 16×16”变成“每像素 4×4”，和场景小人一样细。
- 优点：玩家盯着看的两个地方（说话时的脸、必杀特写）一下子变成高清；**最粗的必杀切入问题直接解决**；场景、战斗、剧情、碰撞完全不动；可以只做主角团和 Boss，NPC 继续用现在的小头像（引擎本来就按头像尺寸排版）。
- 缺点：场景里走来走去的小人还是现在的精度；替身的切入头像也要照这个尺寸重画（样稿没画，切入右半边会暂时一边粗一边细）；每个角色要画 1 张底稿 + 几个表情（嘴张合 2 帧）。

## 工作量估计

全游戏：**91 个角色、996 帧身体（`tools\_meta\chars.json`）+ 175 张头像（66 个角色有头像）**，合计约 1170 张；背景 73 套。
子集：**主角团 6 人**（承太郎 31 / 乔瑟夫 27 / 阿布德尔 20 / 花京院 21 / 波鲁纳雷夫 33 / 伊奇 16 帧 = 148）**+ 替身**（白金之星 19 / 红色魔术师 8 / 绿色法皇 8 / 银色战车 14 / 愚者 7 = 56；隐者之紫是藤蔓特效不用画）**+ 主要 Boss DIO / 世界**（26 + 19 = 45），共 **249 帧**；想再加几个大 Boss（香草冰 + 奶油 17、恩多尔 + 盖布神 9、荷尔·荷斯 10、恩雅婆婆 7）再多约 43 帧。

下面的时间是**粗估**，按两种做法给：“AI 逐像素画 + 人看图挑问题”（就是这次样稿的做法，单位是 AI 会话工时）和“人工像素画师”。每个角色第一帧要定型（定比例、定调色板、定五官），之后的帧在定型稿上改动作。

| 方案 | 全游戏 | 子集（主角团 + 替身 + DIO / 世界） |
|---|---|---|
| 0 现在 | 0 | 0 |
| C 算法放大 | 美术 0；构建步骤 + 引擎世界层改造约 2–3 天 | 同左（算法放大不分子集） |
| A 精度翻倍重画 | 91 次定型 × 2–3 h + 905 帧 × 0.5–1 h ≈ **AI 650–1100 h**；人工 ≈ 91×4 h + 905×1.5 h ≈ **1700 h**；背景要统一的话另算（73 套） | 13 次定型 + 236 帧 ≈ **AI 150–270 h**；人工 ≈ **400 h**；引擎改造另加 3–5 天 |
| B 高清立绘 | 66 个有头像的角色：66 张底稿 × 2–3 h + 约 110 个表情 / 嘴型 × 0.5 h ≈ **AI 190–250 h**；人工 ≈ **600 h** | 13 张底稿（6 人 + 5 个替身 + DIO + 世界）+ 约 30 个表情 ≈ **AI 40–55 h**；人工 ≈ **150 h**；引擎约半天 |

能省工时的地方：原工程的精灵本来就是“零件 + 小骨架”拼出来的（`源码\assets\sprites_jojo.py` 里 `J_HEAD / J_TORSO / j_frame()` 那套）。方案 A 如果先把每个角色的零件（头、躯干、手臂、外套、腿、鞋）按 2 倍画好、骨架坐标乘 2，大部分动作帧能自动拼出来，再逐帧修，子集部分大概能压到上表的一半。这个要先拿承太郎一整套 31 帧试一遍才知道准不准。

## 对现有引擎的影响

### 方案 A / C（世界层 320×180 → 640×360）
世界层尺寸写在 `engine\core.js`（`G.W = 320; G.H = 180`），但 320 这个尺度渗在整个游戏里：剧情脚本里写死的坐标几百处（`story\*.js`、`stages*.js` 的地图 x0/x1/yMin/yMax、`S.setStage` 站位、走位目标）、招式表的判定框 / 射程 / 速度（`engine\moves*.js`）、`combat.js`、镜头、`fx.js / fx_mid.js / post.js` 的特效参数（半径、线数、抖动），还有自动通关测试的快照坐标。两条路：

1. **全部坐标 ×2**：所有数值都要改、所有章节要重测，风险最大，不建议。
2. **只改渲染、逻辑坐标不动（建议）**：逻辑还是 320×180 的单位；只有画的时候世界层是 640×360、坐标 ×2。要改的：
   - `core.js`：世界画布 640×360，合成到屏幕的倍数减半；屏幕倍数必须是偶数才能保持整数放大（现在 s=3 的窗口 960×540 会变成 1.5 倍、像素不等宽，需要改成只用 2 / 4 / 6 倍或接受轻微不均）。
   - `atlas.js`：图集加 `res` 字段（2 = 高清图集，cell / pivot 都是 2 倍，按 1:1 画；没重画的旧图集按 2 倍最近邻画）；光环膨胀、描边宽度、抖动透明要按 `res` 调（光环 grow 1 → 2）。
   - `bg.js`：背景层按 2 倍最近邻画（或以后换成 2 倍背景）。
   - `px.js / fx.js / post.js`：软件光栅是逐像素操作世界层的；要么继续在 320×180 的独立层上画再放大（特效保持现在的颗粒感、性能不变），要么改成 640×360 画（像素多 4 倍，手机上要实测帧率）。
   - `world.js`：坐标 ×2 后可以做到半像素定位，走路和镜头滚动反而更顺；视差取整方式要跟着改。
   - `tools\build_assets.py` / `data_meta`：图集元数据加 `res`；高清图集像素是 4 倍，`data\img_core.js` 现在 1.37 MB，全换的话估计到 3.5–4.5 MB（只换子集会小很多）。
   - 方案 C 额外问题：xBR 混色产生半透明边，`atlas.js` 的光环 / 剪影 / 描边 / 抖动都按 “alpha>0 = 身体” 判断，会多一圈毛边，要在构建时把 alpha 二值化。
   - UI 层本来就是 640×360，不受影响；剧情、招式、地图数据一个不用动。

### 方案 B（只换对话头像和必杀切入）
- `atlas.js` 的 `G.head / G.headSize` 本来就支持非 32×32 的头像（`ui.js` 已经按 `head.h <= 34 ? 2 : 1` 选倍数）。
- **新图用一个新的 key**（比如 `chars/<cid>_bust/<表情>_0|1`），只给对话框和必杀切入用；原来的 32×32 头像继续给 `hud.js` 的队伍头像条和没做高清的 NPC 用，不会把 HUD 撑坏。
- `ui.js` `makeDlg / drawDialog`：有高清立绘时改成“半身压框”版式（立绘底边贴框内底线、头探出框外、后面垫底色、文字起点右移到 162）。
- `ui_cards.js` `renderCutin / drawEnemyCut`：画头像的倍数从写死的 4 改成按尺寸算（128 高的立绘画 1 倍，占位和现在一样）。
- `build_assets.py`：打包新立绘，写进 `headSize`。图片量：样稿这张 128×128 立绘 PNG 是 3.7 KB，子集 40 张左右 base64 后约 200 KB。
- 场景、战斗、剧情、地图、测试全都不动。

## 推荐

**先做方案 B（子集：主角团 6 人 + 5 个替身的切入头像 + DIO / 世界），再看要不要对主角团做方案 A。**

理由：玩家觉得“粗”，最直观的是说话时的大头像和必杀特写——现在必杀切入一个像素 16×16，是全游戏最糊的画面，方案 B 直接把它变成和场景一样细，对话框也立刻有“立绘”的质感；成本只有约 40–55 个 AI 工时 + 半天引擎，场景 / 战斗 / 剧情零风险。方案 A 效果确实最好，但子集也要 150–270 个 AI 工时，而且只做主角会和敌人、背景的像素密度对不上；如果做完 B 用户还嫌场景小人粗，建议走“只改渲染、逻辑坐标不动”的路线，先拿承太郎全套 31 帧试一遍估准工时再铺开。方案 C 花了和 A 一样的引擎成本却几乎看不出变化，不推荐。

## 怎么重新生成

```
cd D:\大疆\游戏素材\JoJo\游戏\docs\美术精度对比\src
python -B make_all.py
```

- `src\common.py`：读游戏图集 / 背景、Scale2x 和 2xBR（numpy 实现）、点阵字（游戏自己的 `assets\font\simsun16.png` + `tools\_meta\font.json`）、`ui.js` 对话框的画法。
- `src\pixart.py`：字母网格画布、2px 描边削成 1px、自动外描边。
- `src\palettes.py`：方案 A / B 的调色板（原色 + 每种材质补 1 级）。
- `src\art_jotaro_a.py`：承太郎重画稿，64×98 逐行逐像素写死的网格。
- `src\art_starplat_a.py`：白金之星重画稿（xBR 底稿定剪影 + 手画脸 / 肌肉线 / 发束 + 统一受光背光）。
- `src\art_portrait_b.py`：承太郎 128×128 立绘（手定多边形 + 五官 / 手指逐像素补丁）。
- `src\scene.py`：按游戏的站位、光环、透明度合成场景；`src\make_all.py`：出全部图；`src\preview.py`：画稿时自查用。
- `_work\` 是画稿时自查用的中间放大图，可以删。

样稿只画了 idle 第 0 帧和一张立绘；呼吸帧、走路等其他动作没画。
